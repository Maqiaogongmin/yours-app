# Yours HarmonyOS Release Pipeline

## Current Rule

The Flutter app at `<repo-root>` is the only
product source. HarmonyOS release work must not be done from
`<legacy-harmony-lab>`.

AGC state is not source truth. AGC can show an edited test description that does
not match the binary uploaded earlier. Treat the local archived APP plus its
metadata as the source of truth for what was built.

## Do Not Touch

The AGC test version that is already in testing for `1.11.4 (11153)` must not be
stopped, updated, or rebound by automation while it is in use.

That version is historical context only. It is not proof that the keyboard inset
fix is present, because the APP package was built before commit `933e327`.

## Canonical Paths

- Flutter source:
  `<repo-root>`
- HarmonyOS shell generated by Flutter-OH:
  `<repo-root>/ohos`
- Release signing and AGC credentials:
  `$YOURS_HARMONY_SIGN_ENV and $YOURS_HARMONY_SIGN_ROOT`
- Release artifacts:
  `$YOURS_HARMONY_ARTIFACTS`
- Release artifact index:
  `$YOURS_HARMONY_ARTIFACTS/README.md`
- New canonical release archive:
  `$YOURS_HARMONY_ARTIFACTS/releases/<versionName>+<versionCode>/<timestamp>/`
- Current latest local release pointer:
  `$YOURS_HARMONY_ARTIFACTS/LATEST_LOCAL_RELEASE.json`

Do not treat `.codex-artifacts/` as a release archive. It is evidence and
scratch space only.

## Version Rule

For each HarmonyOS package intended for AGC testing, increase the build number.

The version must match in:

- `pubspec.yaml`
- `ohos/AppScope/app.json5`

Current next HarmonyOS build number: `1.11.4+11154`.

## Build Only

Use this when the source tree has intentional local version changes:

```sh
make harmony-release-app
```

Use this when the source tree has already been committed and must be clean:

```sh
make harmony-release-app-clean
```

Both targets build and archive the HarmonyOS APP locally. Neither uploads to AGC.
The build target restores `pubspec.lock` after applying HarmonyOS package
overrides, so Flutter-OH dependency patches do not remain in the main source
tree.

Output example:

```text
$YOURS_HARMONY_ARTIFACTS/releases/1.11.4+11154/<timestamp>/
  yours-harmonyos-1.11.4-11154-<gitSha>-release.app
  yours-harmonyos-1.11.4-11154-<gitSha>-release.app.sha256
  metadata.json
```

## AGC Rule

AGC upload and test-version creation must be a separate explicit step after the
local APP exists and has been tested.

Do not reuse the existing `11153` test version for a fixed binary. Create a new
test package/version for `11154` when ready.

Before any AGC write:

1. Read `LATEST_LOCAL_RELEASE.json`.
2. Confirm the APP path and SHA-256.
3. Confirm the target AGC action.
4. Do not update or stop the existing testing version unless explicitly asked.

## Cleanup Policy

- Keep old root-level artifacts as legacy evidence until the new `releases/`
  structure has at least one verified package.
- New production artifacts go only under `releases/`.
- New AGC API evidence should go under a timestamped directory and include
  `summary.json`.
- Do not hard-code one package path in AGC helper scripts.
